REELLIFE — MASTER AI IMPLEMENTATION PROMPT V2

ROLE
You are an AI coding assistant working on ReelLife, a large persistent life-simulation game whose
core vision is “REAL LIFE, BUT A GAME.” You are implementing an existing approved design. Do not
reinterpret the product architecture merely because a different framework, language, or library
would be fashionable or theoretically faster.

PROJECT STATE
The planning phase is complete. This bundle is the source corpus for implementation. ReelLife is
now being built from scratch in its own clean codebase.

CRITICAL IMPLEMENTATION DECISIONS
- Primary implementation stack: web-oriented JavaScript/TypeScript with browser-native HTML/CSS.
- Free-AI-only development constraint: do not make the runtime depend on paid AI APIs/services.
- No existing life-simulator repository is the base.
- robert1811/life-simulator is reference/audit material only.
- Do not recreate the removed stripped starter as the project foundation.
- Other open-source repositories may be researched for patterns, algorithms, or selectively reused
  components only after compatibility and licensing are reviewed; they are not architectural
  authorities.
- Keep the project dependency-light unless a dependency solves a demonstrated requirement.

AUTHORITATIVE DESIGN
The central simulation loop is:

CONDITIONS -> DECISIONS -> EVENTS -> CONSEQUENCES -> NEW CONDITIONS

The implementation pipeline is:

INTENT -> COMMAND -> VALIDATION -> ACTION RESOLUTION -> EVENT -> CONSEQUENCES -> NEW STATE

The player-facing UX loop is:

LIFE -> SITUATION -> DECISION -> CONSEQUENCE -> UNDERSTANDING

ARCHITECTURAL RULES
1. Every persistent state field has exactly one authoritative owner.
2. Systems communicate through defined commands, events, and consequences rather than ad-hoc
   cross-system mutation.
3. Derived state remains derived; do not duplicate authoritative values without a documented reason.
4. Truth, information, perception, interpretation, memory, belief, reputation, and rumor remain
   distinct concepts.
5. Player and NPCs share the same underlying person architecture.
6. Time is authoritative. Scheduled/planned time, activity execution, and actual decisions remain
   distinct.
7. Randomness must be controlled and seedable/serializable where continuity or replay requires it.
   Do not scatter uncontrolled Math.random() calls through authoritative simulation logic.
8. Simulation scale is multi-resolution. Abstract entities may become materialized when relevance
   rises; materialization must restore coherent state rather than invent convenient state.
9. The world continues independently of the player. Avoid player-centric world bending.
10. UI code reads simulation state and dispatches commands; it does not directly mutate simulation
    truth.
11. Organizations, relationships, contracts, assets, information claims, and authority checks are
    shared architectural primitives where the specifications define them as such.
12. Money must be precise and traceable.
13. Death does not erase causal history; life continuity, estate, descendants, and legacy remain
    part of the simulation.
14. Geography is causal and authoritative; maps are presentation.
15. Do not turn the simulation into a collection of disconnected random events or spreadsheet-like
    stat bars.

CONFLICT RULE
If two documents disagree, do not silently merge them. Prefer the higher item in the source
hierarchy above. Current owner decisions override earlier draft suggestions. Preserve the approved
Systems V3 architecture and World Bible. Record meaningful unresolved conflicts for review.

IMPLEMENTATION METHOD
- Build from scratch.
- Establish the simulation kernel before large amounts of content.
- Implement bounded vertical slices that cross multiple systems.
- Prefer clear modules and explicit interfaces over clever abstractions.
- Keep content data-driven.
- Separate authoritative simulation state from indexes, caches, views, and UI state.
- Add tests for ownership invariants, deterministic outcomes, save/load equivalence, and cross-system
  causal chains.
- Add observability early: event tracing, causal paths, state inspection, invariant failures,
  simulation timing, and reproducible seeds.
- Profile before introducing complexity for performance.
- Do not implement all 59 systems at once.

RECOMMENDED EARLY VERTICAL SLICE
Prove a small functioning simulation containing at minimum:
Time + deterministic RNG + authoritative world state + commands/events + persistence + a person +
needs + health + relationships + work/housing/money basics + simple NPC decision-making +
materialization of a small active population + a minimal UI.

The exact implementation order may evolve, but architectural invariants must not.

FREE-AI CODING RULES
When generating code:
- First inspect existing relevant files.
- Reuse existing project conventions when they do not conflict with the source corpus.
- Never invent requirements that the source does not support merely to fill space.
- Never delete an architectural boundary just to make an isolated feature easier.
- Explain consequential architectural changes in code comments or documentation when needed.
- Prefer deterministic tests with explicit seeds.
- Keep changes small enough to review and revert.
- When a requirement is ambiguous, preserve the narrowest behavior supported by the authoritative
  source instead of guessing a broader feature.

REFERENCE-ONLY REPOSITORY POLICY
The previously inspected repository robert1811/life-simulator is not the ReelLife base. It may be
used only to understand what legacy browser life-sim implementations do, or to identify small ideas
worth reconsidering. Do not copy its monolithic state mutation patterns, fixed world data, direct
Math.random() usage, UI/simulation coupling, or feature assumptions into ReelLife.

TECHNOLOGY POLICY
Do not introduce Rust, C++, Python, Unity, Unreal, Godot, or a different primary runtime stack as
an implementation replacement. JavaScript/TypeScript remains the implementation language family.
Browser-native HTML/CSS remain valid foundations. A library/framework/build tool may be considered
only when it clearly solves a project requirement and does not violate the owner's stack decision.

WORLD POLICY
Aurelia is fictional and fully authored by the World Bible. Do not replace it with real-world maps
or Earth geography. World definition is distinct from world state. The world state begins at the
approved game-start configuration and evolves causally.

UI COMPONENT RESOURCE POLICY
The UI component pack is a supporting implementation resource, not a replacement for the UI/UX
specifications. Use bundled shadcn source only where its framework/styling requirements match the
actual ReelLife frontend configuration. Keep component code on the UI side of the simulation
boundary: components render state and dispatch commands; they never directly mutate authoritative
simulation state.

React Bits is reference-only in this corpus. Its current MIT + Commons Clause license permits use
under stated conditions but prohibits redistribution of the components themselves. Do not copy or
bundle React Bits component source into ReelLife distribution archives. Visit the official linked
registry/component pages when a React Bits component is selected for implementation, and re-check
its current license and dependencies at that time.

QUALITY BAR
A feature is not complete merely because it renders. It is complete when its state ownership,
command path, validation, resolution, emitted events, consequences, persistence behavior,
observability, and UI boundary are consistent with the ReelLife architecture and its relevant
system specification.
