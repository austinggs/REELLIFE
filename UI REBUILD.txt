3. NON-NEGOTIABLE ENGINE RULES THE UI MUST RESPECT
---------------------------------------------------------------------

These are enforced by tests in the repo. Breaking them will fail the gate.

R1. ONE WRITER. Each system owns exactly one state slot (systems.<id>) and
    every write asserts ownership through an OwnershipGuard. The UI must never
    mutate world state. UI actions go through the command surface only.
R2. SimulationSession IS THE ONLY DOOR. It is the only module allowed to touch
    the live simulation; everything else receives read-only projections. An
    architecture test enforces this boundary. Do NOT import engine classes
    into components. If a screen needs new data, add a projection to the
    session layer (and test it), not a direct import.
R3. READS MUST NOT WRITE. Engines expose Engine.peek(scope, world) read-only
    handles (Aging, Continuity, Travel, International so far). Use peek-style
    handles for reads; a read that claims a state slot is a bug.
R4. DETERMINISM. Seeded named RNG streams; no Math.random in anything that can
    influence sim state; same seed -> identical stateHash(). UI-only randomness
    (cosmetic particles) must be isolated and must never feed the sim.
R5. SAVE/LOAD EQUIVALENCE. Saves are versioned (SIMULATION_VERSION = 2) with a
    MigrationRegistry and checksums. If you change any save-visible shape you
    MUST bump the version and add a migration + fixture. (M7 forgot once; M8's
    fixture caught it.)
R6. PERFORMANCE BUDGETS are measured in work units, not wall clock. Five
    resolution levels: abstract -> regional -> settlement -> street ->
    household. Provisional resolved-person caps per step: 0 / 64 / 512 / 2048
    / 8192. The UI must render according to the current resolution level and
    must not force the engine to resolve more than the budget allows.
R7. DERIVED vs OWNED. Systems distinguish owned records from derived readings
    (e.g. careReading, settlementReading, caseReading, availability,
    diffusion, standingBetween). The UI should display derived readings as
    readings (with their named binding constraint / basis where provided),
    never cache them as if they were stored truth.

6. SEMANTIC GUARDRAILS — WHAT THE UI MUST NEVER CLAIM
---------------------------------------------------------------------

The project's design culture is: do not overclaim what the model knows. The UI
inherits that. Violations are product bugs, not style issues.

Relationships / people
- No single "reputation score". Reputation is per-observer, per-domain
  perception with decay. Show who thinks what about whom, in which domain.
- Marriage: `spouse` is a relationship CONTEXT. Status is not quality; a
  strained couple can be married with the strain visible. No system holds an
  isMarried flag. Do not add one to the UI state either.
- Conflict "unresolved" is a valid terminal state, not a failure.

Law / security
- A sanction is a CONDITION, not a price. Never show it as a fee that mutates
  a market price.
- Charges reference a law rule id and copy its declared sanction; only a
  CONVICTION applies one. Show charge vs conviction distinctly.
- Government budgets are authorizations only (no magic balances). Policies
  carry an implementation gap; do not present policy as reality.
- Laws are defined per jurisdiction; enforcement/adjudication is elsewhere.

Information / communication
- Information tracks exposure and delivery, NOT belief or comprehension. Never
  render "X believes Y" from a claim unless a system says so.
- Claims have provenance, verification, corrections and disputes; keep them
  visible.

Technology
- Three separate gates: exists -> available -> adopted. An unavailable
  technology cannot be adopted. Show the gate a technology is stuck at.

World / travel / international
- Migration pressure MOVES NOBODY. It is a tendency with direction and causes.
  Crossing belongs to travel; arrival is not citizenship.
- A global shock declares its channel list and stops. Do not animate the
  cascade beyond what other systems actually report.
- Weather is DERIVED (climate zone + season + deterministic jitter), not
  scripted. Disasters currently cause no automatic infrastructure damage
  (logged content gap). Do not draw damage the engine did not record.
- Infrastructure repair follows a strict ladder: workers -> equipment ->
  materials -> access -> authority -> funding. Show the blocking rung.
- Fog of war: the map shows only what the player character knows.

Death / continuity
- Determinations cite evidence (FactRefs). If nothing can be cited it is
  `presumed`, never dressed up as witnessed. Show witnessed vs presumed.
- Estates: will outranks intestacy; intestacy order is descendants ->
  household -> parents -> siblings and stops at the first tier with a
  survivor, and the basis names which relationship applies. Money splits by
  share (integer minor units; remainder named); a single item goes WHOLE to
  the first beneficiary. No living heir -> `unclaimed` (no state fallback).
- Residences, leases, employment and insurance policies are NOT settled by an
  estate (`settable: false`); display them as "stays with its owner", with
  the reason the case gives.
- There is NO `legacyBonus` scalar. Legacy shows up only as concrete fields in
  the owning systems (SUCCESSION_TARGETS). Never invent a legacy score.
- The player's own death is played by the harness; consequences are real
  engine work. Control handoff appends one record and PersonId is not re-keyed;
  the ancestor's causal chain still walks after handoff.
- Provisional mortality numbers (no age-based determination below 65; 2%
  annual hazard at 65, doubling every 8 years, cap 0.6) are NOT canon. If
  surfaced, label them provisional.

Content / canon
- Counts the World Bible does not state are shown as "not stated": GDP,
  named firms/banks/universities, exact city populations, religious shares,
  named wars, technology eras, development stages.
- Settlements: source says both 34 and 30. All 34 are encoded; the
  contradiction is carried. Do not "fix" it in the UI.
- Currency AUR is a shared PROVISIONAL currency. Label it as such in
  settings/debug, and format money via a locale-aware formatter.
- Do not invent named NPCs, feuds, wars or institutions to fill empty states.

7. RECOMMENDED UI STACK
---------------------------------------------------------------------

Decision principle: keep the existing foundation; add specialised libraries
only where the engine's data shapes demand them; treat animated-component
libraries as a thin seasoning layer.

7.1 Foundation (keep; verify actual versions in package.json)
- Vite + React + TypeScript + Tailwind + shadcn/ui components.
- shadcn/ui note: as of 2026-07-03 NEW shadcn projects default to Base UI
  instead of Radix; Radix is still fully supported and every component ships
  for both; the maintainers say working Radix apps need not migrate. If the
  repo is on Radix, do NOT migrate for its own sake; when adding components
  via `npx shadcn@latest add`, confirm which primitive base components.json
  selects so you don't mix flavours unintentionally.
  https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default

7.2 React Bits (expressive layer only)
- What: 165+ free animated components (text animations, animations, UI
  components, backgrounds); delivered as source via the shadcn CLI, e.g.
  `npx shadcn@latest add @react-bits/BlurText-TS-TW`; four variants per
  component (JS-CSS, JS-TW, TS-CSS, TS-TW) -> use the TS-TW variant.
  License: MIT + Commons Clause (free for personal and commercial use;
  cannot resell the library itself). There is also a paid Pro tier
  (application UI, templates, agent kit) — not evaluated.
- Some components pull in GSAP, Three.js or Matter.js; check each
  component's dependencies before adding it and avoid heavy ones on gameplay
  screens.
- One comparison claims React Bits handles prefers-reduced-motion by default;
  UNVERIFIED. Test each component yourself.
- Use it ONLY in the "moment layer" (section 11). Do not use it on dense
  data screens.

7.3 Specialised libraries (add when the phase needs them)
- Motion (`motion` package, formerly Framer Motion): interaction/transition
  animation for app UI (panels opening, confirmations, list reorders).
- Graphs (family tree, causal chains, claim/rumor provenance):
  React Flow (`@xyflow/react`, MIT). Nodes are real React components, so a
  person card can be a node. It does not auto-layout; pair with a layout
  library (dagre or ELK). For 10k+ nodes consider Sigma.js (WebGL) instead;
  Cytoscape.js if you need graph algorithms.
- Map: Aurelia is fictional, so real-world tile stacks are a poor fit.
  Use a flat coordinate system. Recommended first choice: SVG + d3-zoom,
  because there are only 48 countries / 34 settlements, fog-of-war becomes
  per-feature styling, and SVG is keyboard/screen-reader friendly.
  Alternatives: Leaflet with CRS.Simple (image-style maps), or MapLibre GL
  with custom GeoJSON if you outgrow SVG (label collision, vector tiles).
  The engine already decides what the player knows; the map only draws it.
- Long lists (History timeline, Search results, Console log, ledgers):
  @tanstack/react-virtual (headless, ~5KB) or react-virtuoso (richer:
  groups, sticky headers). Avoid react-window (reported as no longer
  actively developed).
- Tables (people directory, ledger, markets): @tanstack/react-table
  (headless). AG Grid is unnecessary.
- Charts (macro, markets, needs over time): Recharts for simple trends;
  visx if custom visuals are needed.
- Command palette / console affordance: shadcn Command (cmdk).
- Icons: lucide-react (already common with shadcn).

7.4 Skip (unless a later requirement forces it)
- Aceternity UI / Magic UI as a core layer: landing-page oriented, Framer
  Motion dependent, overlapping with the above.
- Heavy 3D (Three.js) for core screens.
- Replacing the design system with MUI/Mantine/etc.

8. ARCHITECTURE
---------------------------------------------------------------------

8.1 Data flow
  UI event -> command surface -> SimulationSession -> engine (owner scope)
  engine state -> SimulationSession projection (read-only) -> hooks -> screens

8.2 Binding
- Subscribe to session projections with `useSyncExternalStore` (or an
  equivalent selector hook). Do NOT mirror simulation state in a second
  store (Zustand/Redux). UI-only state (open panels, filters, text scale,
  selected tab) may live in a small local store.
- Projections must be stable/memoised: return the same reference when
  nothing relevant changed, to keep React renders cheap.
- Every projection has: data, a "why" (basis/constraint when the engine
  provides one), and a "coverage" flag (complete / partial / not-stated)
  so screens can render honest empty states.

8.3 Optional (later): run the engine in a Web Worker behind SimulationSession
(the engine is deterministic pure TypeScript). This is a suggestion, not
something seen in the repo. Do it only after profiling shows main-thread
stalls; keep the same projection interface so screens don't change. Any
worker boundary must preserve stateHash equality and save/load equivalence.

8.4 Time and pacing
- Decision surfaces NEVER expire (decisionDeadline returns none). Fast-forward
  and pause are player-controlled. No real-time pressure anywhere.

8.5 Persistence in UI
- Save slots use versioned save format. UI must show slot version, seed,
  in-world date, and surface corrupt-slot / needs-migration states with a
  remedy (playerMessage rule). Never auto-overwrite a slot silently.

10. DESIGN SYSTEM AND ACCESSIBILITY
---------------------------------------------------------------------

Visual direction: NOT DECIDED. Confirm with the owner before styling. Two
candidate directions:
  A. Dossier/ledger: calm, information-dense, editorial, minimal motion.
  B. Atmospheric/game-like: more texture and motion, moments of theatre.
Whichever is chosen, make deliberate, subject-specific choices (a fictional
world, a life, records/law/family) rather than generic SaaS defaults:
avoid the identical-rounded-cards look, decorative gradients, tracked-out
all-caps eyebrow labels on every heading, and one-word headline accents.
Start with a compact token plan: 4-6 named colours, one or two typefaces with
roles, a layout concept per key screen, and a short list of principles.
Critique your plan against the brief before building.

Accessibility policy (already encoded in src/app/ui/accessibility.ts — extend,
do not bypass; add tests when you add surfaces):
- Visual: 4-step textScale applied as ONE root class so every rem-based token
  moves; every meaningful tone carries a text label (never colour alone).
- Motor: >= 44px targets; focus order matches reading order; no timeouts.
- Localisation: formatting as data; no bare numbers interpolated into prose
  (isLocalizationReady); one terminology table (one name per concept).
- Errors: playerMessage must name a remedy. Errors don't apologise and are
  never vague.
- Keyboard: every action reachable without a pointer; visible focus.
- Screen reader: map and graph views need a text/list alternative that
  carries the same information.
- Reduced motion: honour the OS setting AND the in-game preference.
- Responsive: usable down to mobile widths.

Copy rules: plain verbs, sentence case, active voice; name things how the
player understands them, not how the system is built; one name per concept
through the whole flow; empty states explain what is missing and how it
might appear ("No perceptions recorded yet"), and never invent content.

11. MOTION POLICY AND REACT BITS USAGE MAP
---------------------------------------------------------------------

Tier 1 — Response motion (Motion/CSS): opening panels, confirming a command,
expanding rows. Short, purposeful, always reduced-motion aware. Allowed
everywhere.

Tier 2 — Orchestrated moments (React Bits / custom): allowed only in:
- Title / new-life screen (one deliberate reveal).
- Life-stage transitions and birthdays (subtle).
- Death, determination and estate settlement; succession handoff; new
  generation intro (the most "theatrical" allowed moment).
- Loading/save/load feedback.
Each moment: skippable, never blocks input, no time pressure, respects
reduced motion, and shows the same information in plain text.

Tier 3 — Ambient backgrounds/particles: optional, off by default on gameplay
screens, cheap, and disabled under reduced motion or low-power settings.

Never use decorative animation on: People directory, Ledger, History, Law &
Records, Console, Debug.

- Measure with the project's work-unit metrics first; wall-clock only as a
  secondary reading.
